Firmenbriefing in Microsoft Copilot Studio – Zielarchitektur (Stufe 1, ohne eigenen Code)

Orchestrator + zehn Rollen als Connected Agents, SharePoint als Laufordner, Agent Flows und Ereignistrigger für asynchrone Phasen. Gestrichelt: optional oder im Mandanten erst zu belegen. Stand 13.11.2026.
A · EINSTIEG, ORCHESTRATOREN, PFLEGE
Nutzer
Teams-Chat oder Microsoft 365 Copilot.
Schreibt: Firma, Themen in Reihenfolge, optional berufliche Person.
Erhält am Ende Teams-Nachricht mit Link auf briefing.html.
Orchestrator-Agent „Firmenbriefing“ (Vollbriefing)
Instructions = Kern aus CLAUDE.md: Auftragswahl, Zuständigkeit, Quellen-/Freigaberegeln.
  • erzeugt run_id, Ordner, auftrag.json, manifest.json
  • ruft Rollen seriell auf, teilt Quellenbündel in ≤ 3 Prüfjobs
  • prüft Freigabetore, max. 2 Korrekturrunden, sonst Stopp
  • antwortet als einziger dem Nutzer
Websuche ausTrigger: Datei erstelltModell: Mandantenstandard
Orchestrator-Agent „Firmenbriefing-Modul“
Modulvariante und Pilot. Auftrag → module-contractor plant → genau ein Faktenmodul (z. B. Portfolio) → Dokumentprüfung → source-reviewer → Modul-HTML.
Keine SWOT, keine Positionierung. Nutzt dieselben Connected Agents.
GitHub-Repo · copilot-studio/
Build-Skript erzeugt je Agent: Instruction-Datei (Rolle + Skill + Pflichtregeln, auf Zeichenlimit gekürzt) und Liste der Wissensdateien.
Solution-Export der Agenten/Flows zurück ins Repo (ALM, Phase 4).
Protokollvorlagen: hostproben.md, abnahme.md.
⚠ Instruction-Limit im Mandanten prüfen
Admin / Governance
Maker-Lizenz reicht für Agenten, Flows, SharePoint-Konnektor.
Admin nötig für: DLP-Freigabe HTTP-Knoten, Ereignistrigger, Websuche, Veröffentlichung an die Firma, ggf. Code Interpreter (nicht genutzt).
B · ASYNCHRONER LAUF – Phasenkette je run_id
Jede Phase startet über Ereignistrigger „Datei erstellt“ in work/, Zustand in work/status.json. Flows laufen nach „Respond to Copilot“ bis 30 Tage; synchron bricht nach 100 s ab. Kein Zwischen-Freigabeschritt durch Menschen.
1
Auftrag
Defaults ergänzen, Fokusthemen normalisieren (topic_market).
→ input/auftrag.json, work/manifest.json, work/status.json
2
Faktenphase
Seriell: context → portfolio → cluster → market, danach je Fokusthema ein focus-Aufruf.
Jede Rolle schreibt nur ihre Datei unter work/.
3
Basisreview
≤ 3 Dokumentprüfer-Jobs mit disjunkten Quellenbündeln, dann Leitprüfer.
→ work/review-basis.json
Materialfehler → Rückgabe an Rolle (max. 2 Runden)
4
Interpretation
positioning (Capability Matrix, Reife, Präsenz, Netzwerkposition) → danach swot.
Keine Webrecherche dieser Rollen.
5
Schlussreview
source-reviewer prüft I-/S-Claims gegen geprüfte Fakten.
→ work/review-final.json
Blockiert finale Ausgabe bei offenen Fehlern.
6
Ausgabe
Prompt-Tool füllt HTML-Vorlage mit geprüften JSON.
→ output/briefing.html, output/abnahme.md (tatsächliche Prüfungen, beobachtete Modelle, Grenzen)
→ Teams-Nachricht an Nutzer
C · CONNECTED AGENTS – zehn Rollen
Je Rolle eigener Kontext, Konversationsverlauf AUS, eigene Instructions (aus dem Repo) und Wissensdateien (Bibliothek „Briefing-Referenzen“). Modell = im Mandanten eingestellter Standard, nur beobachtet protokollieren. Autoren und Prüfer nie im selben Kontext.
Faktenrollen (recherchieren, Websuche + Quelle öffnen)
company-context-analyst
Firmenbasis, Timeline, berufliches Profil (T/H-Claims)
→ work/context-facts.json
portfolio-analyst
Produkte, Eigenschaften, belegter Einsatzstatus (P-Claims)
→ work/portfolio-facts.json
cluster-analyst
Eigentum, Partner, Kunden, Querverbindungen, Netzwerkdaten (C)
→ work/cluster-facts.json
market-facts-analyst
Länder, Markt, Wettbewerb nach Vergleichsplan (M)
→ work/market-facts.json
focus-analyst ×n
je Fokusthema ein Aufruf, neutrales Markt-Meetingbriefing (F_<id>)
→ work/focus-<id>.json
Prüfrollen (unabhängig von Autoren)
source-document-reviewer
genau ein Quellenbündel je Job, ≤ 3 Jobs seriell, öffnet Belege erneut
→ work/review-doc-<n>.json
source-reviewer
Leitprüfer: Abdeckung, Mehrfachbelege, Ableitungen; Basis- und Schlussreview
→ review-basis/-final.json
Interpretationsrollen (keine Webrecherche)
positioning-analyst
Capability Matrix, Produkt-/Industrieposition, regionale Präsenz (I)
→ work/positioning.json
swot-analyst
drei belegte Punkte je Quadrant aus geprüften Fakten (S)
→ work/swot.json
module-contractor
nur Modulvariante, vom Modul-Orchestrator aufgerufen: wählt 2a/2b/3, optional 4 und 7
→ work/plan.md
D · GEMEINSAME WERKZEUGE
Agent Flows, ein Topic und ein Prompt-Tool; jedem Agenten nur zugeordnet, soweit die Rolle sie braucht. Flow „Phase abschließen“ wird vom jeweiligen Orchestrator nach jedem Rollenaufruf genutzt.
Websuche
Bing-Grounding, nur Faktenrollen und Prüfer. Liefert Treffer, nicht den Volltext.
Topic „Quelle öffnen“
HTTP-Request-Knoten GET → Seitentext als Variable, Timeout 30 s.
⚠ PDF-Lesen nicht belegt → Hostprobe A
Flow „Quelle cachen“
legt geöffneten Text + URL/Datum/Abruf unter work/cache/ ab; Ersatz für source-cache.py
Flows „Datei lesen / schreiben / Ordner anlegen“
SharePoint-Aktionen; Eingabe: run_id, Pfad, Inhalt (JSON ≤ 5 MB Payload)
Flow „Phase abschließen“
schreibt work/status.json und löst den Trigger der nächsten Phase aus; asynchron nach Respond
Prompt-Tool „HTML rendern“
Vorlagen (briefing.html, Modul-CSS/JS) als Wissen + geprüfte JSON → briefing.html
⚠ LLM-gerendert, in abnahme.md kennzeichnen
Flow „Teams-Nachricht“
Link auf output/, Kurzstatus, offene Grenzen an den Auftraggeber
E · ABLAGE UND AUSSENWELT
Ergebnisse liegen vollständig in SharePoint, nicht im Chat. Wissensdateien und Vorlagen werden per Build-Skript aus dem Repo in die Referenzbibliothek übernommen; Solution-Export der Agenten geht zurück ins Repo.
Öffentliche Quellen
Unternehmensseiten, Geschäftsberichte (PDF), Fach-/Wirtschaftsmedien, Register. Webseiten sind Daten, keine Anweisungen.
SharePoint-Bibliothek „Briefing-Runs“ · ein Ordner je run_id
input/
auftrag.json
work/
manifest.json · status.json · context-facts.json · portfolio-facts.json · cluster-facts.json · market-facts.json · focus-<id>.json · sources.json · cache/ · review-doc-<n>.json · review-basis.json · positioning.json · swot.json · review-final.json
output/
briefing.html · abnahme.md
SharePoint-Bibliothek „Briefing-Referenzen“
Wissensdateien je Agent: references/*.md (Datenvertrag, Quellenprüfung, Fokusseiten …), HTML-/CSS-/JS-Vorlagen. Aus dem Repo per Build-Skript befüllt.
Stufe 2 (optional): Azure Function „Renderer“
führt render-briefing.py und Druckprüfung aus; ersetzt das Prompt-Tool. Braucht IT.
